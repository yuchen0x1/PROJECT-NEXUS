# v2.0.0 · PROJECT NEXUS 2.0 — Nine-Center AI Repository Operations Platform

## Summary

PROJECT NEXUS 2.0 reorganizes the 21 existing remote-console pages into nine functional centers without deleting or weakening the underlying capabilities, API contracts, approval gates, persisted data, or isolated worktrees.

## Highlights

- Added the shared `src/nav/centers.ts` registry for the Web sidebar, Electron ActivityBar, and command palette.
- Preserved all 21 legacy pages and verified every leaf through the real Electron desktop shell.
- Added real Settings runtime status for AI provider configuration, model, endpoint, task concurrency, and desktop notifications.
- Added working repository group filters, localized renderer error recovery, i18n toast dismissal labels, and visibility-aware page polling.
- Added per-repository Hosting inspection admission, a shared scan queue pump, and a single Autonomy ticker owner.
- Bounded AI provider requests and responses and rejected unsafe model-proposed integration operations before workspace writes.
- Added ten-language center/settings strings and 12 Web/Electron evidence screenshots.

## Verification

- `npm run check`: 78 test files and 524 tests passed; typecheck, lint, and production build passed.
- `npm run i18n:coverage`: all 10 locales at 100% coverage.
- `npm run i18n:audit`: 0 problems.
- `npm run test:desktop:centers`: passed on real Electron 45.3.4, including all 21 leaves, sidebar collapse/expand, command-palette navigation, language switching, dark/light themes, and real Settings API data.
- See [`PROJECT_NEXUS_2.0_REFACTOR_REPORT.md`](../../PROJECT_NEXUS_2.0_REFACTOR_REPORT.md) for the complete audit, limitations, and evidence index.

## Security and release boundaries

- Observe/repair/autonomous permissions and approval gates are unchanged.
- AI request/response limits are 512 KiB / 2 MiB.
- Model-generated integration operations are validated before entering an isolated workspace.
- User repository Releases and PROJECT NEXUS application updates remain separate workflows.
- The published Windows assets are an unsigned build because this repository does not have an Authenticode signing certificate configured; the release does not claim a trusted publisher identity.

## Known limitations

- Repository, security, and task centers group existing data surfaces but do not merge their independent storage models.
- Real GitHub write operations, real AI provider calls, and 24-hour soak testing remain unverified in the post-release acceptance; see [`POST_RELEASE_ACCEPTANCE_V2.0.0.md`](../POST_RELEASE_ACCEPTANCE_V2.0.0.md).
- The published Windows assets are verified for size and SHA-256, but installation, upgrade, interrupted-update recovery, rollback and user-data retention were not tested on a disposable Windows installation.
- Public Windows publication is owned by `.github/workflows/release-desktop.yml`; future signed releases require the protected signing/publication environments and an Authenticode certificate.
