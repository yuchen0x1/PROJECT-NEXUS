# 技术决策

## 2026-11-21 · 构建与 GitHub 发布权限分离

- **状态**：已实现，等待真实签名发布与安装升级验收。
- **背景**：v0.9.4 的公开 GitHub Release 没有桌面资产；同 tag 工作流拒绝覆盖，而且早期工作流不支持安全续传既有草稿。
- **决策**：唯一正式发布流程使用已合入默认分支的 tag。无写权限的 Windows 任务构建、核验签名与元数据并交接工件；Linux 发布任务串行检查版本、tag SHA 和草稿，再核对所有 GitHub 资产摘要才公开。已有公开 Release 或不匹配草稿一律拒绝。PR 或手动只校验不写 Release。
- **替代方案**：保留单任务会让构建与依赖脚本和发布权限同处一项任务；覆盖不匹配资产会隐藏打包不确定性；通过手动建空 Release 抢先占位会阻断工作流。均不采用。
- **边界**：摘要校验不代替 Authenticode；签名通过不代替旧版本升级及故障回滚。签名凭据只在受控发布构建中使用。另见 [发布管理](RELEASE_MANAGEMENT.md) 和 [对标研究](RESEARCH_LOG.md)。

## 2026-11-21 · 保留本地调度器，按证据恢复

- **状态**：方向已决定，主机租约/关闭顺序等待单独修复。
- **决策**：不引入 Temporal、Windmill 或 Prefect 服务。先保证在打开持久状态前获取所有权，再对有稳定操作 ID、输入摘要且明确可重放的步骤做持久化重试；远端接受状态未知时对账或人工接管，不盲目重放。严格隔离以实际运行器探针为准，失败即阻塞。对比证据见 [研究记录](RESEARCH_LOG.md)。
