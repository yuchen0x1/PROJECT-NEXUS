# PROJECT NEXUS — ULTIMATE EVOLUTION
# Windows AI 自主开发工作站终极进化升级计划

你现在接管的是 PROJECT NEXUS 项目。

项目地址：
https://github.com/yuchen0x1/PROJECT-NEXUS

项目定位：

PROJECT NEXUS 是一款 Windows 原生 AI 开发与项目运营工作站，目标是让 AI 能够理解本地项目、自主研究开源技术、自主规划任务、修改代码、运行测试、修复错误、独立审查，并安全交付最终成果。

当前版本基线为 0.7.0，但必须以当前本地工作区的实际代码、提交记录和配置为准，不能盲目相信 README 中的版本描述。

本次任务不是普通 Bug 修复，而是一次系统级的产品进化。

最终目标：

将 PROJECT NEXUS 升级为真正具备多 Agent 协作、自主研究、自主开发、自主测试、自主维护、自主进化和安全交付能力的 Windows AI 开发中枢。

# 第一阶段：完整接管与现状审计

首先检查当前工作目录。

必须完成：

1. 识别当前实际版本和 Git 分支。
2. 检查 Git 工作区状态。
3. 检查是否存在未提交修改。
4. 阅读 README、CHANGELOG、架构文档和历史交付报告。
5. 完整分析 Electron 主进程、Preload、React 前端、Node 服务端。
6. 分析 Agent Runtime、工具注册体系、Provider、任务队列和工作区隔离。
7. 分析 GitHub API、Webhook、Issue、PR、Release 和更新适配器。
8. 分析 JSON 数据持久化、状态迁移、备份与恢复机制。
9. 检查安全审批、命令执行、凭据管理和权限边界。
10. 检查现有 UI、主题、国际化和任务管理页面。

特别注意：

当前项目已经具备 34 工具 Agent Runtime、Worktree 隔离、独立审查、DPAPI 凭据管理、Provider 路由、GitHub 运营和项目总览等能力。

这些现有能力必须先确认是否真实存在、是否正常工作。

禁止重复开发。

禁止为了追求架构先进而无意义地重构已经成熟的模块。

建立一份完整的功能能力矩阵：

- 已完成且经过真实验证。
- 已完成但只有局部验证。
- 已实现但存在缺陷。
- 已设计但尚未实现。
- 完全缺失。
- 当前架构不支持。

# 第三阶段：多 Agent 协作系统

这是本次最重要的升级方向之一。

目前单一 Agent 负责大量工作，容易出现任务过长、上下文混乱、职责不清和审查不充分的问题。

研究并实现真正的多 Agent 协作架构。

建议建立以下角色：

## 1. Planner Agent

负责：
- 理解用户目标。
- 分解任务。
- 规划执行路径。
- 识别依赖关系。
- 分配任务。
- 评估风险。

## 2. Research Agent

负责：
- 搜索官方文档。
- 搜索 GitHub 开源项目。
- 研究竞品。
- 分析技术实现。
- 核对许可证。
- 收集源代码证据。

## 3. Developer Agent

负责：
- 编写代码。
- 修改代码。
- 重构代码。
- 实现功能。
- 修复 Bug。

## 4. Tester Agent

负责：
- 编写测试。
- 执行测试。
- 检查回归。
- 验证实际功能。
- 分析测试失败原因。

## 5. Security Agent

负责：
- 检查安全风险。
- 检查权限边界。
- 检查敏感数据。
- 检查命令执行。
- 检查依赖漏洞。

## 6. Reviewer Agent

负责：
- 独立阅读最终 Diff。
- 检查代码质量。
- 检查功能完整性。
- 检查测试是否真实。
- 判断是否允许交付。

### 协作机制

必须建立：

- Agent 角色管理。
- 任务分配机制。
- 任务依赖关系。
- 共享任务状态。
- 独立上下文。
- Agent 间消息传递。
- 失败重试。
- 超时管理。
- 预算控制。
- 并行执行。
- 结果汇总。
- 最终仲裁。

不同 Agent 不允许同时无保护地修改同一文件。

必须使用独立工作区或补丁合并机制。

多 Agent 不得互相无限调用。

必须有总任务预算、最大并发数和循环检测。

如果现有模型或供应商不支持某项能力，必须通过兼容层实现，不得假装支持。

# 第四阶段：竞品研究到实际实施的闭环

当前项目已经具备研究能力，但必须进一步实现研究成果自动落地。

建立完整工作流：

发现优秀开源项目
→ 获取项目源码
→ 研究代码结构
→ 识别有价值的功能

→ 核对许可证
→ 创建隔离工作区
→ 实施功能
→ 执行测试
→ 独立审查

每项研究提案必须包含：

- 来源仓库。

- 许可证。
- 参考功能。

- 需要补充的功能。
- 技术实现方案。

增加研究成果状态：

Discovered、Analyzed、Proposed、Approved、Implementing、Testing、Completed、Rejected。

用户批准不等于功能完成。

代码写入不等于测试通过。

测试通过不等于交付成功。

# 第五阶段：PROJECT NEXUS 自主维护与自我进化

建立独立的 Self Maintenance 系统。

让 NEXUS 能够维护自身，但不能让正在运行的程序直接修改自己。

具体能力：

1. 自动识别当前版本。
2. 检查 GitHub 最新版本。
3. 检查本地代码与远程版本差异。
4. 分析自身 Bug。
5. 检查依赖漏洞。
6. 检查过时依赖。
7. 分析代码质量。
8. 检查测试覆盖情况。
9. 检查性能瓶颈。
10. 分析安全风险。
11. 研究同类 AI 开发工作站的新技术。
12. 自动生成自身升级提案。

### 自我修复机制

必须使用独立的 NEXUS 开发工作区。

执行：

自身项目分析
→ 创建隔离分支
→ AI 生成修复方案
→ Developer Agent 修改
→ Tester Agent 测试
→ Security Agent 检查
→ Reviewer Agent 审查
→ 生成升级候选版本
→ 用户确认
→ 安全安装。

不能让 AI 在当前运行实例中直接覆盖核心程序文件。

必须保留上一个可用版本。

如果升级失败，能够恢复到上一个可运行版本。

自我维护策略必须独立于普通仓库托管策略。

# 第六阶段：精确任务恢复与可靠后台

这是必须解决的工程问题。

研究并实现持久化任务状态机。

任务必须记录：

- Task ID。
- 当前阶段。
- 当前执行步骤。
- 已完成操作。
- 待执行操作。
- 工具调用记录。
- 审批记录。
- 远程操作意图。
- 远程操作回执。
- 测试结果。
- 当前工作区。
- 已生成的文件。
- 最终交付状态。

必须支持：

1. 程序崩溃后恢复。
2. Windows 重启后恢复。
3. 网络断开后恢复。
4. 模型服务异常后恢复。
5. GitHub API 限流后恢复。
6. 用户关闭窗口后继续运行。
7. 用户退出程序后安全中断。
8. 重新启动后检查未完成任务。

### 远程操作幂等性

重点防止：

- 重复创建分支。
- 重复提交代码。
- 重复创建 PR。
- 重复合并。
- 重复发布 Release。
- 重复关闭 Issue。

每个外部副作用都必须有唯一操作标识、持久化意图和回执核对。

不确定远端操作是否成功时，先查询真实远端状态，不能直接重复执行。

恢复必须从已验证的安全检查点继续。

# 第七阶段：真正的 Windows 安全执行环境

当前命令允许列表、进程限制和工作区隔离不能等同于 OS 安全沙箱。

研究 Windows 原生安全机制。

重点评估：

- Windows AppContainer。
- Restricted Token。
- Job Objects。
- 独立低权限账户。
- 文件系统 ACL。
- 网络访问限制。
- 进程树限制。
- CPU 和内存限制。
- 命令执行审计。

目标：

让 AI 修改代码时，只能访问授权项目和授权工作区。

不能随意读取用户其他目录。

不能随意访问用户凭据。

不能通过脚本逃逸到宿主环境。

不能绕过审批执行高风险操作。

### 必须区分两种模式

普通模式：
使用当前经过授权的可信本地开发环境。

严格隔离模式：
使用独立低权限环境，限制文件、进程和网络访问。

不能把 Job Object 或允许列表宣传成完整安全沙箱。

如果某项 Windows 安全能力无法可靠实现，必须如实报告限制。

每个阶段必须：

- 有实施计划。
- 有明确代码修改。
- 有真实测试。
- 有回归验证。
- 有交付报告。
- 有下一阶段依赖检查。

如果某阶段存在阻塞，不能伪造完成状态。

### 项目保护规则

1. 不删除已有成熟功能。
2. 不覆盖用户未提交的修改。
3. 不删除用户数据。
4. 不随意改变数据库结构。
5. 不破坏现有十种语言。

10. 不执行不可逆数据操作。
11. 所有升级优先使用独立分支或隔离工作区。
12. 保留原始程序和数据的恢复能力。

涉及安装、证书、系统安全配置、远程发布、数据删除等高风险操作时，必须获得用户明确授权。
